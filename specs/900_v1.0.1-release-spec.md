## 1. Purpose

`crocoexp` v1.0.1 is a reproducible experiment orchestrator for compiling, dry-running, running, and inspecting single-configuration CROCO experiments from immutable input directories.

The first stable release must be narrow, reliable, and explicit about its contract. It must not imply support for the full CROCO ecosystem unless that support is implemented, tested, and documented.

Release philosophy:

```text
crocoexp guarantees reproducible orchestration.
CROCO guarantees the numerical model.
The user guarantees the scientific configuration.
```

For v1.0.1, prefer a boring and reliable release over a broad but fragile one.

## 2. Supported v1.0.1 scope

The v1.0.1 release supports only the following commands:

- `setup`
- `source install`
- `source list`
- `source inspect`
- `source uninstall`
- `experiment list`
- `experiment unimport`
- `import`
- `inspect`
- `compile`
- `dry-run`
- `run`

The v1.0.1 release supports only the following execution modes:

- serial CROCO
- OpenMP CROCO, only if already implemented and tested
- Docker-based execution
- host-side dry-run

The following are explicitly out of scope for v1.0.1 unless fully implemented, tested, documented, and included in the release checklist:

- MPI execution
- XIOS
- OASIS coupling
- GPU
- OpenACC
- full operational workflows
- automatic physical validation
- automatic correction of CROCO input files
- automatic selection of CROCO CPP keys
- automatic tuning of CROCO numerical parameters
- pipeline management
- non-CROCO source families

Unsupported modes must fail early with clear diagnostics.

Suitable v1.0.1 release statement:

> `crocoexp` v1.0.1 is a reproducible experiment orchestrator for compiling and running single-configuration CROCO experiments from immutable input directories. It does not validate ocean physics, does not parse `croco.in`, and does not infer missing NetCDF content.

## 6. Experiment directory contract

Every experiment must follow this layout:

```text
CROCO_EXPERIMENTS/<experiment>/
├── input/       # canonical, user-owned, never modified
├── metadata/    # generated by crocoexp
├── build/       # generated by crocoexp
└── runs/        # generated by crocoexp
```

Required input files:

```text
input/croco.in
input/cppdefs.h
input/param.h
```

Optional supported input files:

```text
input/analytical.F
input/**/*.nc
```

Hard invariant:

```text
input/ must remain byte-identical after import, inspect, compile, dry-run, and run.
```

### 6.1 Generated directories

`metadata/` is generated and managed by `crocoexp`. It may contain experiment manifests, source metadata, import metadata, schema version, command history, and checksums if implemented.

`build/` is generated and managed by `crocoexp`. It may contain staged CROCO source files, staged input files, generated compile artifacts, executable, compile logs, and build manifest.

`runs/` is generated and managed by `crocoexp`. It may contain one directory per run, runtime logs, CROCO stdout/stderr, output NetCDF files, restart files, and run manifest.

### 6.2 Input immutability

The `input/` directory is canonical and user-owned.

`crocoexp` must not:

- edit files inside `input/`
- normalize files inside `input/`
- rewrite `croco.in`
- rewrite `cppdefs.h`
- rewrite `param.h`
- move files out of `input/`
- delete files from `input/`

If staging is needed, files must be copied or linked into `build/` or `runs/`. The original `input/` tree must remain unchanged.

### 6.3 Required validation

Before compile, dry-run, or run, `crocoexp` must check for:

- experiment existence
- presence of `input/`
- presence of `input/croco.in`
- presence of `input/cppdefs.h`
- presence of `input/param.h`
- registered source availability
- supported execution mode

Missing required files must be classified as experiment-contract failures.

## 7. Source contract

A registered compile source must be copied under:

`CROCO_EXPERIMENTS/sources/<source_id>/`

A registered CROCO source must have:

- source ID
- copied source location
- declared version, if supplied
- registration metadata
- inspectable manifest entry

CROCOEXP v1.0.1 source registry accepts CROCO source trees only.

New source records and manifests must not write a `flavor` field. Legacy metadata with `flavor: "croco"` may be read and normalized away. Legacy non-CROCO flavor values must fail with an explicit migration diagnostic because pipelines and non-CROCO source families are outside CROCOEXP scope.

### 7.1 Source registration

`source install` must:

- accept a source path
- accept a stable source ID
- validate that the path exists
- validate required source structure as far as v1.0.1 supports it
- create source metadata
- make the source visible to `source list`
- make the source inspectable through `source inspect`

Repeated source IDs must fail unless `--force` is provided.

### 7.1.1 Source uninstall

`source uninstall <source_id>` must:

- validate that the source exists;
- detect imported experiments that reference it;
- warn and require confirmation in TTY mode when dependents exist;
- require `--force` in non-interactive mode when dependents exist;
- remove the source registry entry and managed installed tree when safe;
- never delete or modify dependent experiments.

Dependent experiments retain orphaned source references and later commands must report those references clearly.

### 7.2 Source inspection

`source inspect <source-id>` must report:

- source ID
- path or managed location
- registration timestamp, if tracked
- declared version, if known
- detected version, if implemented
- availability status
- supported/unsupported status
- reason for unsupported status, if applicable

### 7.3 Source invariants

For v1.0.1, the normal source registration mechanism is a managed copy under:

`CROCO_EXPERIMENTS/sources/<source_id>/`

crocoexp source install must not modify the original source tree provided by the user.

After installation, compile operations must use the managed copy under
CROCO_EXPERIMENTS/sources/<source_id>/, not an arbitrary host path outside the
mounted CROCO_EXPERIMENTS tree.

External-path source registration is out of scope for v1.0.1

All repo-internal operational paths persisted by source and experiment metadata should be repo-root-relative POSIX paths. Absolute external paths are informational only, for example `origin_path`.

Commands must work from the repo root or from any subdirectory inside the repo. The implementation must resolve through repo-root context and must not rely on global `os.chdir()` for normal operation.

### 7.4 Experiment unimport

`experiment unimport <experiment_name>` must conservatively remove CROCOEXP-managed metadata and generated state while preserving `input/`, NetCDF files, and the experiment directory by default. It must reject folders without manifests rather than assuming they are imported experiments.

## 8. Build contract

`compile <experiment>` must:

- refuse to run if required input files are missing
- refuse to run if the requested source is missing
- refuse to run if the execution mode is unsupported
- detect previous compile artifacts before staging
- require explicit `--clean` or `--no-clean` in non-interactive mode when previous compile artifacts exist
- ask whether to clean, keep, or abort in TTY mode when previous compile artifacts exist and neither flag is supplied
- clean only CROCOEXP-managed build artifacts when `--clean` is supplied
- materialize a build directory
- stage `croco.in`, `cppdefs.h`, and `param.h` unchanged
- stage `analytical.F` if present and required by the workflow
- leave NetCDF-like runtime data assets canonical in `input/`
- keep logs under `build/logs/`
- produce an inspectable build manifest
- surface compiler, NetCDF, permission, path, and environment failures clearly

It must not silently modify the experiment `input/` directory.

### 8.1 Build manifest

The build manifest should include:

```json
{
  "crocoexp_schema_version": "1.0",
  "crocoexp_version": "1.0.1",
  "experiment": "<experiment>",
  "source_id": "<source-id>",
  "build_id": "<build-id>",
  "mode": "serial|openmp|docker",
  "status": "success|failed",
  "logs": []
}
```

### 8.2 Compilation failure categories

Compilation failures must be categorized as compilation/environment failures when caused by:

- missing compiler
- bad compiler path
- bad library path
- NetCDF not found
- NetCDF incompatible
- missing executable permissions
- wrong script header
- full disk or home space
- memory or stack limitation
- unsupported execution mode
- missing source files

`crocoexp` should not try to solve these problems automatically in v1.0.1. It must preserve logs and classify the failure clearly.

### 8.3 Binary requirement

A successful compile must result in a known executable path recorded in the build manifest. If no executable is produced, the compile command must fail.

## 9. Dry-run contract

`dry-run <experiment>` must:

- verify required input files
- verify registered source availability
- verify expected binary state when relevant
- detect unsupported modes when possible
- detect unsupported CPP symbols when implemented
- report planned execution steps
- report the command that would be executed, if safe to show
- support JSON output if documented
- fail with documented nonzero exit codes

Dry-run must not run CROCO.

Dry-run must not modify:

- `input/`
- CROCO source tree
- existing run directories

Dry-run may create metadata only if this is documented and deterministic.

### 9.1 Unsupported mode detection

If MPI, XIOS, OASIS, OpenACC, GPU, or other unsupported modes are detected or requested, dry-run must fail early unless that feature is fully supported by the v1.0.1 implementation.

The failure must explain:

- which feature is unsupported
- where it was detected, if known
- whether the user must change `cppdefs.h`, CLI options,

### 9.2 Dry-run JSON

If `--json` is promised for `dry-run`, the output must be valid JSON and must include at minimum:

```json
{
  "status": "ok|error",
  "experiment": "<experiment>",
  "checks": [],
  "planned_actions": [],
  "errors": []
}
```

## 10. Run contract

`run <experiment>` must:

- refuse to run without a compiled binary
- refuse to run if required input files are missing
- refuse to run if the execution mode is unsupported
- create a unique run directory
- preserve logs under `runs/<run_id>/logs/`
- preserve output files under the run directory
- produce run metadata
- never mutate `input/`

Runtime blow-ups are CROCO/model-level failures, not `crocoexp` contract failures, unless `crocoexp` incorrectly staged or executed the run.

### 10.1 Run directory

Each run should be placed under:

```text
CROCO_EXPERIMENTS/<experiment>/runs/<run_id>/
```

Recommended structure:

```text
runs/<run_id>/
├── logs/
├── output/
├── restart/
├── manifest.json
└── command.txt
```

The exact layout may differ, but it must be documented and inspectable.

### 10.2 Runtime failure categories

Runtime failures must be categorized separately from compilation failures.

Runtime failures may include:

- missing executable
- executable not runnable
- CROCO exits nonzero
- CROCO blow-up
- missing runtime file
- missing NetCDF dependency
- bad path inside `croco.in`
- Docker runtime failure
- permission failure
- output directory failure

`crocoexp` must preserve logs even when the run fails.

### 10.3 Output expectations

For the BASIN smoke test, a successful run should produce CROCO output files such as restart and history NetCDF files, unless the specific test configuration uses different output names or disables those outputs.

The smoke test must document what files are expected and where they are stored.

## 12. Exit-code categories

Every nonzero exit must map to a documented category.

Required categories:

- invalid CLI usage
- missing experiment
- invalid experiment contract
- missing required input
- missing source
- duplicate source ID
- Docker unavailable
- unsupported execution mode
- unsupported source metadata
- compilation/environment failure
- missing binary
- CROCO runtime failure
- internal `crocoexp` error

The actual numeric exit codes must be documented in `contract.md` and repeated or referenced in the manual.

Recommended baseline:

```text
0  success
1  general failure
2  invalid CLI usage or missing argument
3  missing required artifact, missing source, missing binary, unsafe/missing file
4  metadata, registry, staging, report, manifest, or workdir preparation failure
5  actionable policy or registry failure
7  Docker/backend failure
8  compile failure
9  CROCO runtime failure
```

## 13. Required tests

The v1.0.1 release must include a minimal but serious test matrix.

### 13.1 Unit tests

Unit tests must cover every command's failure modes.

Required unit-test cases:

- missing `croco.in`
- missing `cppdefs.h`
- missing `param.h`
- missing source
- missing binary
- bad Docker availability
- bad experiment name
- duplicate source ID without `--force`
- `--json` output validity where promised
- unsupported source metadata
- unsupported execution mode
- invalid CLI arguments
- invalid experiment layout

### 13.2 Contract tests

Contract tests must verify:

- `input/` is never modified
- `build/` can be deleted and regenerated
- `runs/` can be deleted and regenerated
- NetCDF files are symlinked, not copied, unless explicitly documented
- `croco.in` is copied unchanged
- `cppdefs.h` is copied unchanged
- `param.h` is copied unchanged
- `manifest.json` is deterministic enough to inspect
- logs are preserved for failed compile
- logs are preserved for failed run
- expected nonzero exit codes are produced

### 13.3 CROCO smoke tests

Mandatory smoke test:

- BASIN import
- BASIN compile through `crocoexp`
- BASIN dry-run through `crocoexp`
- BASIN run through `crocoexp`
- BASIN inspect through `crocoexp`

The BASIN smoke test must verify expected output or document why the output is different for the selected configuration.

Optional smoke test:

- one realistic or semi-realistic case only if data size, licensing, and runtime are acceptable.

Do not include large realistic-data workflows as release blockers unless the data are reliable, small, and legally distributable.

### 13.4 Expected-failure tests

At least one expected-failure test must be included for:

- missing NetCDF input
- bad `croco.in` path
- unsupported MPI/XIOS/OpenACC mode
- missing binary at run time
- compilation/environment failure

The test must verify that the error category is correct and that logs are preserved.

## 14. Release-blocking acceptance criteria

Do not tag `v1.0.1` until all of the following are true:

- `./crocoexp --help` is complete and consistent.
- Every documented subcommand works.
- Every subcommand has `--json` only where implemented and promised.
- Every promised `--json` mode emits valid JSON.
- Every nonzero exit has a documented category.
- The manual matches the actual CLI, not the intended CLI.
- The README example works by copy/paste from a fresh clone.
- BASIN imports through `crocoexp`.
- BASIN compiles through `crocoexp`.
- BASIN dry-runs through `crocoexp`.
- BASIN runs through `crocoexp`.
- BASIN inspection works through `crocoexp`.
- Unsupported MPI/XIOS/OpenACC modes fail early.
- `run` refuses to proceed without a compiled binary.
- `input/` remains byte-identical after import, inspect, compile, dry-run, and run.
- Logs are stored under `build/logs/` or `runs/<run_id>/logs/`.
- Common CROCO compilation failures are surfaced as compilation/environment failures.
- `contract.md` exists and matches this spec.
- `docs/user_manual.md` exists and matches the actual CLI.
- `CHANGELOG.md` contains the v1.0.1 entry.
- `LICENSE` exists.
- `CITATION.cff` exists.
- Release candidate has been tested from a fresh clone.
- No half-implemented feature is visible as a stable promise.

## 19. Release philosophy

For the first stable release, make `crocoexp` boring.

It should not be clever.  
It should be trustworthy.

The correct separation is:

```text
crocoexp guarantees reproducible orchestration.
CROCO guarantees the numerical model.
The user guarantees the scientific configuration.
```

That separation is what makes `v1.0.1` credible.
